# Context Engineering — 컨텍스트 엔지니어링 Skill

AI-사용자 간 소통에서 발생하는 정보 비대칭, 가정 불일치, 인지 과부하를 체계적으로 관리한다.

---

## 트리거 키워드

"컨텍스트", "혼란 관리", "가정", "context engineering", "progressive disclosure", "소통 품질", "정보 정리"

---

## 3가지 핵심 프로토콜

### 프로토콜 1: 혼란 관리 (Confusion Management)

불확실한 점이 발생하면 즉시 구조화하여 제시한다:

```
CONFUSION:
{무엇이 불확실한가}

Options:
A) {선택지 1} — {장단점}
B) {선택지 2} — {장단점}
C) 사용자에게 질문 — {이유}

→ 어떤 접근을 선호하시나요?
```

**적용 시점**: 요구사항 모호, 선택지 다수, UX 동작 불확실

**[절대 금지]**: 불확실한 상태에서 가장 그럴듯한 옵션을 선택하여 진행

### 프로토콜 2: 가정 표면화 (Assumptions Surfacing)

작업 시 세운 가정을 반드시 명시한다:

```
ASSUMPTIONS:
1. {가정 1}
2. {가정 2}
→ 틀린 것이 있으면 지금 교정해주세요. 이대로 진행합니다.
```

**적용 시점**: 기획 수립, 기능 범위 결정, 데이터 구조 해석, UX 동작 추론, 외부 서비스 동작 가정

**[절대 금지]**: 가정을 밝히지 않고 작업을 진행하는 것

### 프로토콜 3: 점진적 공개 (Progressive Disclosure)

정보 과부하를 방지하기 위해 단계적으로 정보를 제시한다:

1. **요약 먼저**: 3줄 이내 핵심 결론
2. **상세는 요청 시**: "상세 내용이 필요하시면 말씀해주세요"
3. **질문 그룹화**: 한 번에 3~5개 (10개 한꺼번에 절대 금지)
4. **진행 상황 보고**: 긴 작업 시 중간 보고 (Phase 전환 요약)

## 워크플로우

### 1단계: 현재 컨텍스트 평가

- 사용자 요청에서 **명시적 정보** vs **암묵적 가정** 분리
- 답할 수 있는 부분과 답할 수 없는 비즈니스 결정 목록 작성

### 2단계: 컨텍스트 보강

- 제공된 문서/자료 분석
- 관련 기존 결정사항 확인
- 가정 목록 작성

### 3단계: 컨텍스트 동기화

- ASSUMPTIONS 프로토콜로 가정 확인
- CONFUSION 프로토콜로 불확실 해소
- Progressive Disclosure로 정보 전달

### 4단계: 실행 후 컨텍스트 검증

- 결과가 사용자의 의도와 일치하는지 확인
- 불일치 시 재동기화 (어디서 인식이 갈렸는지 분석)

## 컨텍스트 계층 (Context Hierarchy)

```
┌─────────────────────────────────────┐
│  1. Rules Files (CLAUDE.md, rules/) │ ← 항상 로드
├─────────────────────────────────────┤
│  2. Skill Files (SKILL.md)          │ ← 트리거 시 로드
├─────────────────────────────────────┤
│  3. 관련 문서/자료                   │ ← 작업별 로드
├─────────────────────────────────────┤
│  4. 사용자 피드백/답변               │ ← 반복별 로드
├─────────────────────────────────────┤
│  5. 대화 히스토리                    │ ← 누적, 자동 압축
└─────────────────────────────────────┘
```

**원칙**: 상위 레벨일수록 안정적이고 하위 레벨일수록 휘발적이다. 상위 레벨에 기록된 규칙이 우선한다.

## 자기합리화 방지 (Anti-Rationalization)

| 자기합리화                      | 현실                                                                |
| ------------------------------- | ------------------------------------------------------------------- |
| "사용자가 원하는 걸 알고 있다"  | 명시적 확인 없는 이해는 추측이다                                    |
| "질문하면 사용자를 귀찮게 한다" | 잘못된 결과를 되돌리는 것이 더 귀찮다                               |
| "컨텍스트는 충분하다"           | 충분하다고 느끼는 순간이 가장 위험하다                              |
| "문서를 보면 의도를 알 수 있다" | 문서는 "무엇"을 말하지 "왜"를 말하지 않는다. 의도는 사용자에게 확인 |

---

## 위험 신호 (Red Flags)

이 스킬 실행 중 아래 신호가 보이면 즉시 멈추고 재검토한다:

- 사용자의 요청을 한 번도 확인하지 않고 작업을 시작한다
- 가정을 세웠지만 명시하지 않는다
- 10개 이상의 질문을 한꺼번에 던진다
- "당연히 이렇겠지"라고 생각한다
- 사용자가 "그게 아니라"라고 2회 이상 교정한다 (컨텍스트 동기화 실패)

---

## 완료 증거 (Verification)

아래 항목이 모두 충족되어야 완료:

- [ ] 가정 목록을 사용자에게 제시하고 확인받음
- [ ] 불확실 사항에 대해 CONFUSION 프로토콜 적용
- [ ] 질문 그룹이 3~5개 이내
- [ ] 사용자가 결과에 동의함 (재작업 요청 없음)
      "이해했습니다"는 증거가 아니다. 사용자의 확인만 증거다.

---

## 핵심 규칙

1. **가정은 반드시 표면화**: 암묵적 가정은 문제의 근원
2. **질문 과부하 방지**: 3~5개씩 그룹화
3. **결과 검증**: 작업 후 사용자 의도와 일치하는지 확인
4. **"왜"를 묻는다**: 무엇을 만들지는 문서가 알지만, 왜 만드는지는 사용자만 안다
